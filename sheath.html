The structure in one sentence

Four phases, not four features

The five requirements — configuration over the network, several distributions, netboot installation, fixed addresses, monitoring — are not a feature list. They are the stations of a lifecycle, and the system is built along it.

Phase 1Provision Empty NVMe → netboot → mini-OS writes the assigned image
→
Phase 2Configure Agent pulls its desired state every 60 s and applies it idempotently
→
Phase 3Monitor Inside view from the agent, outside view from the server — status on the LED and in the UI
→
Phase 4Rebuild Assign a different distribution → reimage → back to phase 1

The one decision from which everything follows: the server owns an image catalogue, and the distribution is an attribute of the blade — blade-03.image = dietpi-arm64. That makes “several distributions” no longer a build problem but a row in the database. Without a netboot installer it would be ten times the manual work; with it, it is a dropdown.

Phase 1

Netboot, Mini-OS, NVMe

The pivot sits in the EEPROM: BOOT_ORDER=0xf26 means “NVMe first, then the network, then start over”. An empty NVMe therefore falls through to netboot by itself — no switching over, no button, no cable.

1
Bootloader
NVMe is empty → netboot. DHCP supplies the address and the TFTP server.
2
TFTP
From the directory named after the serial number: kernel, device tree, cmdline.txt and a mini initramfs. A few tens of MB, no more.
3
Mini-OS
Reads the CM4 serial number and asks the server: POST /api/v1/provision/{serial} → image URL, SHA-256, layout, token.
4
Mini-OS
Writes over HTTP: curl … | zstd -d | dd of=/dev/nvme0n1, verifies the checksum, expands the root partition.
5
Mini-OS
Seeding offline: mounts the freshly written root partition and puts the agent binary, systemd unit, server URL and blade token straight into it.
6
Blade
Reboot, boots from NVMe, the agent reports in → online.

The iron rule: nothing large over TFTP

This is not a matter of taste. There are three documented reasons:

  • A hard size limit. The bootloader's TFTP block counter overflowed at 64 K blocks — with a block size of 1468 that is at around 96–114 MB. Fixed only with the bootloader of 23.09.2025. An initramfs that is too large simply fails on older bootloaders.
  • No retry. NET_BOOT_MAX_RETRIES is 0 from the factory: after a TFTP timeout the netboot does not start again, the blade stays dark. Set it to a value > 0.
  • No windowing. The client uses blksize up to 1468, but no RFC 7440 windowsize — one block per round trip. Hence the slowness.

Only kernel, device tree and initramfs therefore go over TFTP; the image comes over HTTP from the already running mini-OS. No NFS root, no image over TFTP. That is the difference between “works in the lab” and “works on ten blades at once”.

The TFTP directory per blade — and a trap inside it

TFTP_PREFIX=0 (the factory setting) makes the bootloader look in a subdirectory named after the lower four bytes of the serial number — eight hex digits, not the full sixteen-digit serial: 

/tftpboot/9ffefdef/{start4.elf, fixup4.dat, config.txt, cmdline.txt,
                    bcm2711-rpi-cm4.dtb, overlays/, kernel8.img, initramfs}

The trap: if the bootloader finds no start4.elf there, it discards the prefix silently and loads from the TFTP root. An empty blade directory therefore leads not to an error but to the wrong boot.

Two network pitfalls

STP on managed switches is the classic netboot killer: after link-up the switch checks for loops for about 30 seconds, which makes the boot take minutes or fail. Set portfast, or edge port, on all blade ports. And: TFTP is unsecured and belongs exclusively in the management VLAN.

Do not build the mini-OS yourself

Raspberry Pi already supplies this part: the scriptexecute initramfs from raspberrypi/usbboot — a minimal Linux that starts, runs a script handed to it and then exits. It is exactly the “utility operating system image” that Raspberry Pi describes in its own provisioning documentation, and the basis on which cmprovision works too. We adopt it and only replace the script with sheath-installer, a small static Go binary using the same API library as the agent. A Buildroot or Alpine initramfs of our own is thus dropped entirely.

For a truly dead blade the USB route remains as a fallback: mass-storage-gadget from the same project exposes the NVMe as USB mass storage and writes faster than classic rpiboot. That does need a cable and a human at the rack, though.

Reinstalling a running blade

The CM4 has no one-time netboot — set_reboot_order is expressly “Raspberry Pi 5 only” according to the documentation. Two routes remain, both without touching the EEPROM:

  • kexec — the agent fetches the installer kernel and initramfs over HTTP and jumps straight into it. Bypasses bootloader and TFTP completely. It requires CONFIG_KEXEC in the kernel of the respective distribution — so with three distributions it has to be checked three times.
  • tryboot — a genuine one-shot in the firmware: reboot '0 tryboot' loads tryboot.txt once instead of config.txt, and the flag is cleared before the start. A crash leads automatically back to the normal configuration. In return the installer has to sit on the NVMe boot partition, not on the network.

Recommendation: kexec as the primary route, tryboot as the fallback. From the rack's point of view nothing visible happens either way — except that the LED switches to provisioning.

Several distributions

Three extension points, nothing else

Multi-distro gets expensive when distribution knowledge seeps through the whole codebase. It stays cheap if you lock it into named places. There are exactly three of them — and none of them lies in the core.

A
Server · pure data

Image catalogue

URL, SHA-256, partition layout, seed method per distribution. Taking on a new distribution means: drop in the image, enter the checksum. No code.

B
Installer · ~20 lines

Seed adapter

Puts the initial configuration into the freshly written image. In practice the same generic adapter for all three — see below.

C
Agent · one interface

Platform adapter

Hostname, users, packages, units. One base debianFamily covers all three; DietPi inherits and overrides its own peculiarities.

The great simplifier: seeding happens offline

In version 1 the first boot was the most distro-dependent part of all — cloud-init on Ubuntu, dietpi.txt on DietPi, something else again on Debian. This whole block falls away, and for an incidental reason:

The installer has the root partition mounted and writable anyway. It can copy the agent straight into it — binary, systemd unit, token. There is no need for cloud-init, no dietpi.txt, no sysconf.txt. The day-0 bootstrap shrinks to a file copy that works identically on every systemd distribution.

Concretely that is four file operations in the mounted root partition:

install -m755 sheath-agent   $ROOT/usr/local/bin/
install -m644 sheathd.service $ROOT/etc/systemd/system/
install -m600 blade-token.env     $ROOT/etc/sheath/
# Enabling a unit without a running systemd = the symlink by hand:
ln -s /etc/systemd/system/sheathd.service \
      $ROOT/etc/systemd/system/multi-user.target.wants/sheathd.service

The last step is the only one that is not obvious: systemctl enable creates nothing more than exactly this symlink, and you can set it yourself offline. Because the agent binary is statically linked, the same procedure works on glibc and musl systems alike.

The distro-native adapters remain as an option — worthwhile only if you want to take along distribution-specific features, such as DietPi's software installer. As the standard route the generic one is recommended for all three.

The blade says what it is

With every heartbeat the agent reports a set of facts, taken from /etc/os-release plus a bit of probing. The server can use it to tailor configuration per distribution, and the rack view shows per slot what is running there. 

facts:
  os_id:         dietpi | debian | ubuntu
  os_version_id: "13" | "24.04"
  os_family:     debian          # this is what the platform adapter keys on
  init:          systemd
  pkg_mgr:       apt
  net_backend:   networkd | ifupdown | netplan | NetworkManager
  boot_path:     /boot | /boot/firmware

packages:                       # exit for diverging package names
  - name: htop
  - name: linux-cpupower
    per_os: {ubuntu: linux-tools-common, debian: linux-cpupower}

What the three images actually bring with them

The following details come from dissecting the real Ubuntu image — FAT32 parsed directly, ext4 via debugfs, DTBs decompiled — as well as from the package and documentation sources of the other two.

What lies on the boot partition

The conclusion of the research in one sentence: a clean common denominator across all three does not exist. Ubuntu has a real, documented seed on the boot partition; newer Debian images have none at all; DietPi has one of its own, a very powerful one — which however keeps writing back.

That is precisely the justification for the generic adapter. It sidesteps the problem instead of solving it three times: whoever writes into the root partition anyway does not need the distribution's seed mechanism at all.

Two confirmations for the procedure

A simple dd is enough. The Ubuntu cmdline.txt looks for the root via root=LABEL=writable … rootwait, that is, medium-agnostically. The image can be written to the NVMe unchanged and boots from there without anything having to be adjusted.

The CM4 needs no config.txt change for NVMe. In the decompiled bcm2711-rpi-cm4.dtb the PCIe node has no status property, so it is okay by default; the supplied config.txt consequently contains not a single NVMe or PCIe line. dtparam=nvme and PCIE_PROBE=1 are Pi 5 topics — there the DTB says status = "disabled". For us that means: normally the installer does not have to touch the boot partition at all.

The special case DietPi

DietPi manages a great deal itself: dietpi-config, dietpi-software, its own network and hostname handling, dietpi-update. An external configuration management that touches the same files leads to a wrestling match that both sides lose.

Rule: the agent touches nothing that DietPi owns. On DietPi, the network stays with DietPi — the DHCP default suffices, because the fixed address comes from the reservation anyway. The agent restricts itself to hostname, SSH keys, its own files and its own units.

An open risk to be checked before anything else

By default DietPi builds no initramfs (SKIP_INITRAMFS_GEN=yes). Ubuntu loads the NVMe driver as a module from the initrd — if the initrd is missing, NVMe has to be compiled into the kernel, otherwise DietPi does not find its root and does not boot at all. Whether the DietPi RPi kernel does that is unverified.

First test, before anything at all is built: write a DietPi image onto an NVMe and see whether it boots. If the test comes out negative, DietPi either needs a forced initramfs or it drops out as an NVMe distribution. The rest of the architecture would remain untouched — it would be one row fewer in the image catalogue.

An honest measure of the effort

All three distributions named are Debian family: apt, dpkg, systemd. The effort is therefore considerably smaller than “multi-distro support” sounds — at heart one base implementation plus a handful of DietPi exceptions. The installer of compute-blade-agent already recognises dpkg, dnf and pacman and fits without change. It would only get really expensive with Alpine (musl, OpenRC, apk), Fedora or Talos, which has no shell at all. The interface holds the door open without paying for it today.

Fixed addresses

Three routes, one of them manageable

It is assumed that the RPi bootloader can only do DHCP when netbooting. That is not true. Since the bootloader of March 2020 there has been a static configuration in the EEPROM — if CLIENT_IP, SUBNET, GATEWAY and TFTP_IP are set, DHCP is skipped. So there are three routes, not two.

Routes to a fixed address
RouteCentrally manageableDHCP neededAssessment
DHCP reservationyesyesRecommendation
Static in the EEPROMno — per device, only via rpibootnoRobust, but every change means: open the rack
Static in the OSyes, but distro-dependentfor the netboot all the sameThe worst route

The reason against the EEPROM is not technical but operational: the address would then sit in ten individually generated EEPROM images, and once write protection was enabled it would be nailed down. Software that is supposed to manage addresses can do nothing with that.

Sheath owns the address management and generates DHCP reservations from it: slot 3 → 10.10.0.13 → dhcp-host=<mac>,10.10.0.13,blade-03. The same dnsmasq instance does boot options, reservation and name resolution.

The second, more important reason

Network configuration is the most distro-divergent part of all — netplan on Ubuntu, /etc/network/interfaces on Debian and DietPi, plus systemd-networkd and NetworkManager. If the fixed address comes from the reservation, every distribution simply does DHCP, and this whole block of topics disappears from the agent. So the decision does not only buy clean addresses, it also takes the most expensive lump out of extension point C.

Doing both — reservation and static in the OS — is the worst route: the reservation degenerates into documentation, the OS ignores it, and whoever changes only the reservation creates an address that exists nowhere. One truth, not two.

Proxy DHCP is not enough

An obvious wish: dnsmasq only does the boot part, the existing router carries on handing out addresses. That does not work. The dnsmasq documentation is unambiguous — in proxy mode “another DHCP server on the network responsible for allocating IP addresses” applies; there dnsmasq supplies exclusively the PXE information and hands out no addresses at all. dhcp-host has no effect whatsoever on allocation in proxy mode.

It follows that: the blades go into their own VLAN, and there dnsmasq is the authoritative DHCP server. The router on the house network stays untouched, because it is not responsible for this segment at all — which is advisable anyway, since TFTP is unsecured.

Changing reservations at runtime

Sheath writes the reservations from the inventory; dnsmasq reads them without a restart: dhcp-hostsdir=/etc/dnsmasq.d/blades/, one file per blade. New or changed files are picked up by dnsmasq by itself. One drawback: deleted or rewritten entries only disappear with a SIGHUP, because host records are only added dynamically. Sheath therefore additionally sends a systemctl reload dnsmasq after every removal.

Chicken and egg — the shortcut is barred

On the Pi 3 and older the MAC could be derived from the serial number. From BCM2711, that is the CM4, that has gone without replacement; the Raspberry Pi documentation says so expressly: “the MAC address is programmed at manufacture and there is no link between the MAC address and serial number.” In exchange there are three better ways out:

  1. Assign the MAC yourself. The EEPROM property MAC_ADDRESS overrides the factory-programmed address. During the one-off bring-up every slot gets a deterministic MAC from the locally administered range — say 02:b1:ad:00:00:03 for slot 3. MAC, IP and slot are then known before the first boot and the problem no longer exists. The most elegant solution.
  2. A small dynamic pool. An unknown blade gets a loan address, netboots, enrolls itself — from the next boot the reservation takes effect. Always works and needs no preparation.
  3. Read the serial number from DHCP option 97. The bootloader packs it in there: FourCC RPi4, board revision, the lower four bytes of the MAC and the four bytes of the serial number — according to the documentation meant for exactly this, to identify Pis “without relying upon the Ethernet MAC OUID”. dnsmasq cannot derive an address from it, though; that would need Kea with flex-id.

Recommendation: route 1, with route 2 as a safety net.

The exception

The one piece of manual work that remains

Everything described so far runs without access to the rack. Exactly one step does not — and that one should be planned deliberately instead of discovered.

The CM4's factory setting is BOOT_ORDER=0xf641, not the desired 0xf26. As long as that stays so, an empty blade does not fall through to netboot in the first place. And changing the EEPROM from the running system is not the intended route on the CM4: rpi-eeprom-update is disabled there from the factory, and the documentation warns that the self-update is not atomic — a power cut during it damages the EEPROM. For a fleet that is no routine tool.

So once per blade, over a USB cable and rpiboot, before it goes into the rack:

BOOT_ORDER=0xf26                  # NVMe → network → loop
NET_BOOT_MAX_RETRIES=3            # factory is 0: no retry after a TFTP timeout
MAC_ADDRESS=02:b1:ad:00:00:03     # deterministic from the slot — solves chicken-and-egg
TFTP_PREFIX=0                     # directory = lower 4 bytes of the serial number

That takes a few minutes per blade and is never needed again afterwards. Sheath can generate the EEPROM configuration from the inventory, so that the bring-up is one command — bmctl eeprom-config --slot 3 — and not hand editing. While you are at it, update the bootloader too: for initramfs files beyond about 96 MB you need a build from 23.09.2025 or newer.

After that, for the whole rest of the lifecycle: plugging it in is enough.

Phase 2

Configuration during operation

Unchanged from version 1 — it sits well with everything that has been added.

  • Pull instead of push. The agent asks for its desired state every 60 s, applies it idempotently and reports back. No SSH access on the server, converges by itself after every reboot.
  • Three levels, merged: global → group → blade.
  • Hash comparison. The server delivers the merged config with a hash, the agent reports the applied hash back. Drift detection falls out of that at no extra cost — the Status column in the rack view is exactly this comparison.
  • Hardware stays with the compute-blade-agent (Go, Apache-2.0): LEDs, fan, button, critical mode on over temperature, Prometheus on :9666, gRPC with mTLS. Sheath only writes its config.yaml and calls its API for identify.

Phase 3

Monitoring from two directions

A dead blade cannot report its own death. That is why the agent's heartbeat is not enough — a second, independent observation from outside is needed.

Inside view — the agent reports every 60 s: SoC temperature, fan speed, exhaust temperature, uptime, load, disk usage, NVMe SMART, config hash, agent version, the PoE indicator on GPIO23 and optional service checks.

Outside view — the server observes for itself: age of the last heartbeat, ICMP and TCP probe, active DHCP lease and, if the switch offers it, link status and PoE power of the port via SNMP.

The state of a blade is its worst individual check — and that is exactly what lights up on the edge LED. Rack view and metal show the same information.

Escalation

The heartbeat stops → the server probes actively → the switch reports power at the port, but no network traffic arrives → suspicion of a hung operating system → proposal of a power cycle over the PoE port. Default: only after confirmation, with a rate limit of at most one cycle per blade per hour. Automatic repair can be switched on, but is not the default — a blade in a boot loop should not also be hard powered off every five minutes.

Notification

ntfy, a webhook or e-mail are enough for ten blades. Prometheus and Alertmanager are only worth it if they are in the house anyway; the compute-blade-agent already supplies the metrics in the right format, Sheath provides the target list via HTTP SD.

Interfaces

Three audiences, three auth models

# Provisioning — called by the mini-OS
POST /api/v1/provision/{serial}          → image URL, sha256, layout, seed, token
POST /api/v1/provision/{serial}/status   → writing 45 % | verifying | done

# Agent — one bearer token per blade
POST /api/v1/enroll
GET  /api/v1/blades/{serial}/config      merged desired config + ETag
POST /api/v1/blades/{serial}/status      heartbeat, facts, health values
GET  /api/v1/blades/{serial}/commands    reboot | identify | reimage

# Management — UI and CLI
GET/PUT /api/v1/blades/{serial}
PUT     /api/v1/blades/{serial}/image     change distribution → triggers a reimage
POST    /api/v1/blades/{serial}/actions/{identify|reboot|reimage|power-cycle}
GET     /api/v1/images                   catalogue
GET     /api/v1/health                   overall state of the rack
GET     /api/v1/prometheus/targets       HTTP Service Discovery

The three levels stay separate, so that a compromised blade token can do nothing more than report its own state — read no one else's configuration, trigger no action.

Deliberately not chosen

  • cmprovision as a basis. A factory tool: “write this image onto fifty modules”, and then it is done. No ongoing desired state, no heartbeat, no roles. On top of that it aims at eMMC instead of NVMe and demands an isolated network segment, because it provisions by broadcast. From this ecosystem we take what is valuable — the scriptexecute initramfs — and leave the Laravel application out.
  • MaaS or Tinkerbell. Full-blown bare-metal provisioning including UEFI PXE, oversized for ten blades.
  • Ansible. No self-enrollment, no heartbeat, needs SSH and known addresses. Can be added later; Sheath then supplies the dynamic inventory.
  • Network configuration in the agent. Made superfluous by the DHCP reservation — and that was the most distro-dependent part.

Roadmap

Five steps, each usable on its own

Step 0

Bring-up

Once per blade over rpiboot: BOOT_ORDER, NET_BOOT_MAX_RETRIES, MAC_ADDRESS. Switch ports to portfast.

→ the prerequisite for everything else
Step 1

Server and agent

Inventory, image catalogue, config merge, REST. Agent with enroll → pull → apply → status. bmctl. Image still written onto the NVMe by hand.

→ configuration over the network, three distributions in parallel
Step 2

Addresses

dnsmasq generated from the inventory: DHCP reservations, fixed addresses, DNS records.

→ addresses are fixed and in one place
Step 3

Netboot chain

TFTP per serial number, scriptexecute, sheath-installer, image delivery over HTTP.

→ plugging it in is enough, distribution from a dropdown
Step 4

Monitoring

Health model, rack UI, alerting, reimage via kexec, optionally a PoE power cycle.

→ state in view, remote maintenance possible
Step 5

Cluster

The roles k3s-server and k3s-worker as group config.

→ blades as Kubernetes nodes

Step 2 comes before step 3, because netboot presupposes the DHCP service anyway — both land on the same dnsmasq instance.

To be settled before the start

Open points, by urgency

Settled by the research: Sheath has to take over DHCP for the blade VLAN, because proxy DHCP hands out no addresses. On the CM4 the MAC cannot be derived from the serial number — instead assign it yourself via MAC_ADDRESS. There is no one-shot netboot on the CM4. The CM4 needs no config.txt change for NVMe. And a plain dd of the Ubuntu image onto the NVMe boots unchanged.

  1. DietPi on NVMe — the very first test DietPi builds no initramfs; without the NVMe driver built into the kernel it does not find its root. Write an image onto an NVMe and let it boot, before anything at all is built. A negative outcome costs one row in the image catalogue, no design.
  2. Check the Debian image Is root locked, is openssh-server installed at all? For the generic adapter it makes no difference — it does not depend on SSH — but it does for emergency access.
  3. kexec per distribution The reimage route stands or falls with CONFIG_KEXEC in the respective kernel. Where it is missing, tryboot takes over.
  4. Bootloader build of the ten blades For large initramfs files a build from 23.09.2025 onwards is needed — bring it along during the bring-up.
  5. A managed PoE switch with SNMP or an API? Only then are a power cycle and the outside view of the port available. Independently of that: portfast on all blade ports, otherwise netboot becomes unreliable.
  6. NVMe models Check against the compatibility list in the Compute Blade documentation — not every SSD runs on the CM4.
  7. Watch, do not act Ubuntu's seed trick relies on fs_label: system-boot; cloud-init has marked exactly that as deprecated since 24.3. Works today, keep an eye on it for 26.04 — it only concerns us if we do use the cloud-init adapter after all.

Address plan

Proposal: slot n → 10.10.0.(100+n), MAC 02:b1:ad:00:00:0n, hostname blade-0n, TFTP directory by serial number. Every quantity can then be derived from every other — except the serial number, which comes from the hardware and is linked in the inventory.
